# 2026-10-11 搜索-读文件配对率实测

研究动机：评测洞察修订把配对率定为前置指标——「用日志当考题集」能否成立，先看真实搜索事件里有多大比例能配上「搜索后打开的文件」这个真值。本实验只量配对率，不构造考题集。

实测日期 2026-10-11。数据源：hsa 的 `data/cleaned/search_events.parquet` 与 `messages.parquet`（同一批 29550 条搜索事件，见 [hermes-session-analyzer 研究记录](2026-10-11-hermes-session-analyzer.md)）。

## 口径

配对 = 搜索事件之后、下一条用户消息之前，首个非搜索工具调用是读文件类工具。归因逻辑直接复用 hsa cleaner 的 `_followup`：它返回的就是「搜索后首个非搜索动作」。

读文件类工具按来源归一：zed/hermes 是 `read_file`，pi/dsh/opencode 是 `read`（dsh 另有 `read_image`）。bash `cat` 不计入——它是 shell 行为，归入边界声明而非配对。

## 数据规模

hermes 与 hermes-backup 的 session_id 不同名，但 backup 的查询串 100% 与 hermes 重复（2596/2596）——同一行为的双计，整体剔除。去重后：

- 搜索事件 25386 条，含搜索的会话 541 个
- 配对事件 3364 条，总配对率 **13.3%**
- 会话级：78.4% 的会话（424/541）至少有一次配对

搜索后首个非搜索动作的分类：shell 64.5%、读文件 13.3%、其他工具 12.5%、无动作 9.7%。

## 关键发现

**1. 原始 `read_after` 字段低估了配对率。** hsa 原口径只认 `read_file` 这一个工具名，得 7.8%；归一化各来源读文件工具名后为 13.3%。用配对率做任何决策前必须先过归一化这一步。

**2. 配对率高度集中在专用搜索工具上：专用搜索 51.0%（1597/3132），shell 命令仅 7.9%（1767/22254）。** 原因不言自明：grep/find 的结果本身就是命中内容，AI 读完输出就拿到了答案，不需要再打开文件；专用搜索返回的是路径列表，必须打开才有内容。所以「不打开文件」对 shell 不是失败，对专用搜索才是弯路信号。

**3. 考题集应建在专用搜索的配对子集上。** 专用搜索事件 3132 条、配对率 51%，约可支撑 1600 题的考题集——规模充足，构造可行。

## 可判定结论

**配对率足以支撑考题集构造**：在专用搜索配对子集（约 1600 题）上建考题集可行。这套评估的适用边界随之明确：它评估的是专用搜索行为（我们的搜索工具对标的正是这一层）；shell 搜索行为（占搜索总量 87.8%）不在其内，那部分 AI 直接从命令输出拿答案，不经过「搜索工具」这一层。

## 口径限制

- 「打开的 = 想要的」是假设，本次未校验——AI 可能凑合打开第一个看着相关的文件。抽样人工校验是下一步，顺序在构造考题集之前。
- 打开的文件路径未抽取：需要解析五种来源的原始会话格式（共约 900MB），留给考题集构造步骤。
- bash `cat` 读文件不计入配对，读文件率是下界。
- zed 来源拿不到工具结果，无法区分「搜到才打开」与「没搜到也打开」。
- 本机单人样本，非产品流量。
