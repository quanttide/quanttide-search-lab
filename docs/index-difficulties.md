# 索引的难点

一句话定义：索引不是「文档的清单」，是一份**会过期的副本**，而且它的打分是**全局统计量**——任何一处内容变了（多一篇、重复一篇、漏一篇），所有查询的排序跟着变，还不报错。

2026-10-10 本机实测。原型跑法见 [tech-notes.md](tech-notes.md)，能力边界见 [README.md](../README.md)。

## 真题：同一查询，两种索引

查询 `tantivy`：

```
干净索引（索引目录只跑一次）
    13.147  …/search-lab/docs/tech-notes.md
     9.163  …/search-lab/AGENTS.md

同一索引目录再跑一次（全部文档被重复加入）
    13.222  …/search-lab/docs/tech-notes.md
    13.222  …/search-lab/docs/tech-notes.md   ← 同一文件两行
     9.215  …/search-lab/AGENTS.md
```

白话：BM25 的分数不是「这篇文档好不好」，是「这篇在当前这批文档里相对多重要」。副本均匀翻倍还算运气——排序没乱；真实场景里镜像不均匀（`assets/` 多一份、`domains/` 少一份），排序就错位，而你只会看到结果「有点怪」，看不到任何错误。

## 三个难点

### 一、该索引什么

遍历只收 `.md` 扩展名，代码、JSON、配置一律不进索引。实测：`struct Config` 在多个 `.rs` 文件里，查询返回 0 条——**漏索引永远无声**，用户不会收到「没索引」的提示，只会以为内容不存在。

这是领域定位里「可索引化」的实体：哪些内容该进索引，是先要回答的问题，而且判据已经在 README 里——这条内容删掉后能否从别处重建。

### 二、副本要等于真相

三个病同一个症状（错了不报，只把分数算歪）：

- **去重**：同一文件的子模块镜像各占一席，前十名成对出现。
- **幂等**：同一索引目录跑第二次，副本翻倍、分数漂移（上例 13.147 → 13.222）。
- **增量**：文件改了、删了，索引不知道——就是日志说的「搜索引擎会不断过时、更新速度太快」。

### 三、凭什么说改好了

索引数据一动，全部排序都动。没有一批「查询 → 期望结果」的评测，每次改索引都是盲改：只能看「变了」，看不出「好了」。日志里「和数据一起改」的后半句必须是判据，否则那个「可以改进搜索算法的元系统」无从谈起——它也同时是「纯 RAG 对照」实验（README 流程第一条）的前置：没有评测集，「RAG 对企业需求不顶用」这条判断无法验证。

## 顺序

先修幂等（不修，后面测的都是假数）→ 建评测查询集（元系统的最小实体）→ 治理镜像去重。第 2、3 件正是本域定位里「索引的新鲜度与一致性」和「质量评测」的正身。
